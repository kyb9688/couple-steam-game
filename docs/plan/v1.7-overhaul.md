# TrashCleaner3D v1.7 개편 기록 (2026-11-27)

기준 커밋: `backup/v1.6-before-200nodes` (= `ddfd12c`, v1.6)
대상: `unity/TrashCleaner3D/Assets/_Project/Scripts`(C#), `docs/qa/*v17*`
비대상: `docs/webgl/` — Unity 에디터가 없는 환경이라 WebGL 재빌드는 사용자 PC에서 해야 한다.

## 0. 이번 개편의 세 가지 축

1. **공짜 효과 제거** — v1.6까지 기본으로 주던 부가 효과(연쇄 흡입, 봉투 피버/현금, 산소 부스트, 정산 콤보, 대량 정산 보너스 등)를 전부 **기본 0/잠김**으로 돌리고 강화 노드로만 해금.
2. **220노드 강화 트리** — 코어 28 + 마이크로 192(8계열 × 4가지 × 6단계). UI는 휠 줌 0.22x~1.5x + 뷰포트 컬링 + 8계열 색상.
3. **4시간 캠페인 밸런스** — 방 사용 면적 확장, 웨이브 기반 물량(누적 19.3만 개), 1회 강화당 1~3% 상승, 스테이지 보상 배수 0.35→0.12.

## 2. 강화 트리 220노드

- 데이터 단일 출처: `docs/qa/tree_v17.py` → `docs/qa/gen_upgrade_tree_v17.py` → `Assets/_Project/Scripts/UpgradeTreeV17.cs` (C# 데이터 테이블 자동 생성, 시뮬레이터도 같은 데이터를 읽는다).
- 구성: **코어 28** (도구 3티어, 차량 3단계, 대걸레, 로봇, 피버엔진, 수거통·단가 등 기존 진행축) + **마이크로 192** = 220노드.
- 8계열: 흡입·손 / 수거·정산 / 큰 봉투·타격 / 얼룩·행주질 / 방독면·산소 / 피버·콤보 / 로봇청소기 / 차량·운송. 계열마다 4가지 × 6단계가 중심에서 사방(±1,300px)으로 뻗는다.
- 1회 상승폭: 1.5~3% (해금형은 1레벨). 초반 두 단계는 레벨 5까지 열어 두어 '싼 구매거리'가 항상 남는다.
- 가격: 단계별 배수 0.22 / 0.9 / 3.0 / 9.0 / 26 / 70 × 계열 기본가(200~360), 레벨업 ×1.30. 마이크로 노드 전 레벨 총비용 **$3.66M**.
- UI(`PrototypeHudUI.DrawUpgradeKioskTree`):
  - 휠 줌 **0.22x~1.5x**(기본 0.30x 개요), 드래그 팬, `[R]` 초기 위치, 줌 배율 표시.
  - **뷰포트 컬링**(노드·연결선 모두), 축소 시 텍스트를 생략하고 색 점으로 그려 220개 가지 흐름이 한눈에 보이게 함.
  - 8계열 색상 범례 + 축소 상태에서 계열 이름표(중심 반경 470px) 표시.
  - 정적 메타데이터(이름·설명·좌표)는 1회만 생성하고 매 프레임 레벨·가격만 갱신(IMGUI 비용 절감).

## 3. 방 확장 · 물량 · 페이싱

- `InstancedTrashSwarm.RoomZoneDef`를 **방 끝까지** 넓히고, 원래 있던 화장실·복도·욕실·대표실·탕비실·2층 랜딩·3층 금고방을 별도 구역으로 포함했다.
  - 사용 면적: ST2 +31%, ST3 +12%, ST4 +80%, ST5 +48%, ST6 +27%, ST7 +55% (씬 벽체는 그대로).
- **웨이브 스폰**: 스테이지별 총물량을 한 번에 만들지 않고 1,130~6,500개 단위 웨이브로 공급.
  - 웨이브가 10% 이하로 비면 다음 더미가 쏟아지고(`무너진 더미에서 또 쏟아졌다!`), 방 클리어 연출은 모든 웨이브가 끝난 뒤에만 발생.
  - 청소된 슬롯 재사용(`_freeSlots`) → 누적 13만 개 물량에도 배열·순회 비용은 동시 생존 수(최대 6,500)만큼만 든다.
  - 정적 인스턴스 청크 재구축을 0.18초로 스로틀(3만 개 시대의 CPU 스파이크 방지).
- 스테이지 총물량: 960 / 2,700 / 7,020 / 18,690 / 24,000 / 10,170 / 130,000 = **193,540개**.
- 큰 봉투·얼룩: 8/30/20/36/45/30/60개, 얼룩 5/10/40/20/24/16/30개 (씬 원본이 모자라면 런타임 복제).

## 4. 밸런스

- 1회 강화당 상승폭을 1~3%로 낮추고 홀드 커브를 1.00→0.80(코어 10레벨 합계 -20%)로 완만하게 바꿨다.
- 스테이지 보상 배수 `1 + (stage-1)×0.35` → `×0.12`.
- Python 시뮬레이션(`docs/qa/balance_sim_v17.py`) 결과: **226.5~227.1분**, 구매 640~687회, 구매 간격 p90 29~30초.
- 상세 표와 가정: `docs/qa/balance_report_v17.md`.

## 5. 검증과 한계

- UnityEngine 참조 어셈블리 Roslyn 컴파일: 기본/`UNITY_WEBGL` 모두 **오류 0**.
- 트리 검증: 고립 노드 0, 순환 참조 0, 미정의 선행 0.
- **한계**: Unity 에디터가 없어 실제 1인칭 플레이·WebGL 빌드 확인은 못 했다. 시뮬레이터는 이동·조준 손실을 효율 계수(0.50~0.62)로 근사한 이산 모델이므로 절대 시간은 사용자 PC 실측에서 ±20% 흔들릴 수 있다.
- 씬 벽체·문 위치는 baked 상태라 실제 벽을 허물지는 않았다. '방 확장'은 **플레이 가능한 바닥 구역을 방 끝까지 넓히고 쓰이지 않던 방을 포함**한 형태다. 벽 자체를 넓히려면 `StageSkeletonBuilder`로 씬을 재생성해야 한다(에디터 필요).
